# Lorrator

**由 LLM 驅動的 TRPG 跑團平台。**

Lorrator（Lore + Narrator）把劇本知識、角色卡與即時對局收進同一個系統，讓 AI 擔任守門人（KP），主持一場以《克蘇魯的呼喚》為主的調查冒險。玩家負責扮演與抉擇；系統負責讀懂劇本、記住世界狀態，並即時回應桌上發生的事。

---

## 解決什麼問題

一場傳統跑團高度依賴 KP：他要先消化整本劇本，記住 NPC、地點、線索與隱情，再開桌時同時敘事、判定與控節奏。劇本一長，準備成本與記憶負擔就會急遽上升。

本專案 -- Lorrator 把「讀懂劇本」交給管線，把「當場主持」交給語言模型。

---

## 三件事構成一次完整體驗

**劇本知識庫。** 上傳劇本後，系統會轉成 Markdown，再走一條可逐步檢視的處理管線：讀取原文、切塊、抽取實體與關係、寫入知識圖譜、產生向量、合併近似實體。圖譜裡會出現角色、地點、陣營、物品、事件等節點，以及它們之間的關聯。使用者可以在劇本頁查看文件、實體與圖譜，也能回看每一步的處理結果。

**角色卡。** 目前實作以 CoC 7e 為主，涵蓋屬性、技能、職業與技能點。角色資料以彈性結構存放，同一套帳號可以管理多張角色卡，進房時再選要用哪一張。

**AI 守門人與即時房間。** 從劇本開房、用邀請碼召集同伴、選角並就緒後即可開團。KP 依劇本敘事、推動調查，並在需要時要求技能檢定，但不會替玩家擲骰、也不會替角色做決定。聊天、骰子與 KP 回覆透過 WebSocket 同步到所有人桌上。每一輪對話另會摘要已發生的事，協助系統記住已揭露的事實與未解線索。

---

## 一場團怎麼跑

1. 建立或挑選角色卡  
2. 建立劇本、上傳文件，等待知識圖譜建好  
3. 從該劇本開一個房間，把邀請碼傳給同伴  
4. 全員選角、按就緒，由房主開團  
5. AI KP 開場；玩家以角色發言、調查、擲骰  
6. 系統依劇本與當下狀態回應，直到這場調查告一段落  

KP 的工作原則很明確：先描述場景、再把選擇權交回玩家；需要檢定時只說明要擲什麼、為什麼，真正的骰子由系統擲出後再交回敘事。線索不會過度提供，但也不該因為過度保密而讓故事走死。

## 系統結構

```
前端（Vue 3）
    │  REST + WebSocket
    ▼
後端（FastAPI）
    ├── PostgreSQL + pgvector   帳號、房間、角色卡、文件與向量
    ├── Neo4j                   劇本知識圖譜
    ├── OpenAI API              KP 敘事、實體抽取與摘要
    └── model-serving           Cross-Encoder 重排序
```

前端以 Vue 3、Vite 與 Pinia 打造，視覺走調查員檔案式的低調風格。後端負責帳號、劇本、文件管線、房間狀態與即時推播。文件先由 MarkItDown 轉成可處理的文本，再進入圖譜建構；向量存在 PostgreSQL，圖存在 Neo4j。獨立的 model-serving 提供重排序模型。

目前開團時，KP 以劇本內容為權威來源來主持；知識圖譜、嵌入與重排序「讓系統理解劇本」，技術核心則是把長篇劇本變成可檢視、可擴充的世界模型。
